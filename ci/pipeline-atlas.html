Gate 0 — does a pipeline exist at all

The entry gate

Before any job is considered, workflow:rules decides whether GitLab creates a pipeline. The global variable MAINTENANCE is the kill switch: set it to "true" and every automatic trigger stops, while manual ones still work.

Consequence for feature branches

A push to feature/* creates nothing. To test a feature branch you need a web, api or merge_request_event pipeline — which is also why those three ignore MAINTENANCE.

The branch that actually branches

Where the platform lands

Two variables decide the whole deploy stage: whether DEPLOYMENT_INSTANCE_FQDN is empty, and whether exec_server_installation is true. They select which of three mutually exclusive readiness checks runs, whether a Harvester VM is created, and whether anything gets destroyed at the end.

Why build and deploy can be split

The only handover is a tag in the registry

Nothing is passed from build to deploy as an artifact. Both stages independently compute the same version string from git, and the registry is the meeting point — which is what makes exec_build: false with exec_deploy: true a valid configuration, and what makes it fail fast when that commit was never built.

The configuration surface

Known-good configurations

Six shapes worth naming

These are the combinations that produce a coherent pipeline. Anything else is reachable, but check it against the matrix above first.

The nightly

schedule · develop · all defaults

34 jobs. Tests, then build, then a fresh Harvester VM, install, deploy, integration tests, destroy. About 41 minutes to reach the build, most of it the UI e2e matrix serialised on one runner.

# nothing to pass — every default is already this shape

Preflight only

api · feature branch · under a minute

Two jobs. Checks the CI variables, then SSHs the target and reports whether it is ready — before a single image is built. What exec_redeploy: false does on an occupied target shows up here.

glab ci run -b feature/ci-deploy-any-target \
  -i 'exec_unit_tests:bool(false)' \
  -i 'exec_build:bool(false)' \
  -i 'exec_integration_tests:bool(false)' \
  -i 'exec_deploy:bool(true)' \
  -i 'exec_server_installation:bool(false)' \
  -i 'exec_redeploy:bool(false)' \
  -i 'deployment_fqdn:e230-pc11.inet.dkfz-heidelberg.de' \
  -i 'deployment_user:m395c'

Build only

any branch · up to 8 h

One job. Pushes images and charts under this commit's git describe tag, which a later deploy-only run can pick up.

glab ci run -i 'exec_unit_tests:bool(false)' \
  -i 'exec_deploy:bool(false)' \
  -i 'exec_integration_tests:bool(false)'

Deploy an already-built commit to your own box

api · needs the commit built earlier

Skips tests and build entirely. prepare_deployment probes the registry for the chart first, so a commit that was never built fails in seconds. The target is never destroyed.

glab ci run -i 'exec_unit_tests:bool(false)' \
  -i 'exec_build:bool(false)' \
  -i 'exec_deploy:bool(true)' \
  -i 'exec_server_installation:bool(false)' \
  -i 'exec_redeploy:bool(true)' \
  -i 'deployment_fqdn:e230-pc11.inet.dkfz-heidelberg.de' \
  -i 'deployment_user:m395c'

Keep the VM to poke at it

adds 4 h to the pipeline's life

destroy_deployment becomes when: delayed, so the VM survives long enough to log in after a failure.

glab ci run -i 'exec_destroy_delayed:bool(true)'

Release

push a tag X.Y.Z — no inputs involved

The tag alone forces build_packages on and swaps REGISTRY_* for the release triple through rules:variables, plus a forced docker system prune for a cold build. This works only because no REGISTRY_* project variables exist — a project variable outranks rules:variables, which is what broke the 0.7.0 release.

git tag 0.7.1 && git push origin 0.7.1
# requires RELEASE_REGISTRY_URL / _USER / _TOKEN — preflight_variables checks them on tag pipelines

Edges that bite

Seven things the rules do not say out loud

1

An FQDN with exec_server_installation: true gets no readiness check and a sudo install on your workstation. preflight_target's rule requires !install; target_readiness's requires an empty FQDN. Neither fires.

2

DEPLOYMENT_SSH_KEY without an FQDN is rejected in preflight. A provisioned Harvester VM only accepts the kaapana keypair, so a per-run key can only reach a target you name.

3

An FQDN over 57 characters fails, twice. dcmsend rejects longer peerhosts. The input's own regex catches it at merge time, preflight_variables checks the variable, and prepare_deployment checks it again.

4

CI_REGISTRY_USER shadows a GitLab-predefined variable. If the project variable is ever deleted, jobs silently receive gitlab-ci-token and every push is denied — which is why preflight fails explicitly on that exact value.

5

Re-pushing an existing CI_IMAGES_TAG leaves warm runners on the stale image. Runners pull if-not-present, so a change under ci/images/** has to land with a tag bump in the same MR.

6

The global GIT_DEPTH: 1 breaks git describe. Any job that needs the version — both build jobs and prepare_deployment — must override with GIT_STRATEGY: clone and GIT_DEPTH: "0".

7

New jobs must be added to two needs: lists by hand. destroy_deployment is the teardown barrier — anything touching the VM belongs there or the VM dies underneath it — and if_ci_failing lists all 32 jobs, because when: on_failure with needs: only watches the jobs it needs.
